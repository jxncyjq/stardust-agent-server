## 一、已完成（全部合入 master，可直接信任）

### 1. A5c 插件安装与授权语义

**「装了」和「能跑」不再是一件事。**

- server [#86](https://github.com/jxncyjq/stardust-agent-server/pull/86) → `f22c0be`
- docs [#7](https://github.com/jxncyjq/stardust-agent-docs/pull/7) → `812bbb7`
- Plan：`docs/superpowers/plans/2026-08-24-plugin-install-and-consent.md`

`agent plugins install` 只登记来源与摘要，**默认零授权**；`grant`/`deny` 是独立的显式动作。

**落盘编码（这是后续一切的基础，改错会静默破坏语义）**：

| 磁盘形状 | 含义 | `status` 显示 |
|---|---|---|
| `enabled:false`，**完全没有 `grant` 字段** | 已登记，从没人决定过 | `unauthorized` |
| `enabled:false`，**`grant` 字段仍在**（能力已清空） | 决定过，撤销了 | `disabled` |
| `enabled:true` + 能力齐全 | 已授权 | `loaded` |

判据是 `Entry.GrantStated`（由 `ParseDeployment` 按 `grant` 键是否出现填充），**不是**「capabilities 是否为空」——纯计算插件本来就零能力。

### 2. GUI 授权同意流

**运维能从 GUI 授权插件，而 GUI 不会成为第二条各说各话的授权路径。**

- server [#87](https://github.com/jxncyjq/stardust-agent-server/pull/87) → `cc41662`
- GUI [#22](https://github.com/jxncyjq/stardust-agent-gui/pull/22) → `0b63a5a`
- docs [#8](https://github.com/jxncyjq/stardust-agent-docs/pull/8) → `eecfe0f`
- Plan：`docs/superpowers/plans/2026-08-25-gui-plugin-consent.md`
- Spec：`docs/superpowers/specs/2026-08-25-gui-plugin-consent-design.md`

结构：所有能力/主机/路径规则住在 `internal/plugin/consent`，CLI 与三个 HTTP 端点调同一批函数。`internal/server` **永不** import `internal/plugin/loader`。

**四种结果不是三种**（端点先写盘再收敛，故除写盘失败外磁盘都已改）：

| # | 情形 | 响应 |
|---|---|---|
| 1 | 写盘失败 | 4xx/5xx，磁盘未动 |
| 2 | 收敛完成 | 200 |
| 3 | 收敛**没跑**（等超时/取消/另一个 apply 在跑） | 200 + `pending_convergence: true` |
| 4 | 收敛跑了但这一条激活失败 | 200 + `state: failed` |

判据是 `taskgate.ErrBoundaryNotReached` 专属哨兵，**不是** `context.DeadlineExceeded`——后者会从收敛内部的 `fetch.Fetch` 冒出来，两者在错误链上结构等价。

### 4. 插件声明的主动取回

**未缓存的远程插件不再是 GUI 里的死路。**

- server [#88](https://github.com/jxncyjq/stardust-agent-server/pull/88) → `c9feeec`
- GUI [#24](https://github.com/jxncyjq/stardust-agent-gui/pull/24) → `8a4c0c0`
- Plan：`docs/superpowers/plans/2026-08-27-plugin-resolve-declaration.md`
- Spec：`docs/superpowers/specs/2026-08-27-plugin-resolve-declaration-design.md`

`POST /v1/plugins/{name}/resolve` 取回并验签，**到此为止**：不碰 `plugins.json`、不写 grant、不触发收敛。

**关键设计**：

- `manifest.ErrUntrustedPackage` 挂 `verifyManifestSignature` 的**三条**路径（签名缺失、不可解析、验不过），**第四条（读 `plugin.sig` 的 I/O 错误）刻意不挂**——磁盘故障是可重试的环境问题，混进信任信号会让真正的安全事件贬值。
- 不可信 → `server.ErrPluginUntrusted` → **HTTP 422** → GUI **不给重试**（重试一万次签名还是不对）。
- `PluginView.DeclaredUnresolvedReason` 说明是**哪一种**未解析（`not_cached` / 无缓存配置 / 加载失败）——只有第一种取回有用。
- RBAC 用 `write_plugin`，按**副作用**归类（发出站请求 + 往缓存写盘），不是按「改没改授权」。

**真机验证结果**（本会话最后做的，后端全通过）：

```
declared_unresolved_reason = "not_cached"      ← 服务端说明是哪一种
resolve → 200, declared=["log","tool"], granted=null   ← 看见了，没授权
plugins.json 一字未动（无 grant 段）
包落在 cache/sha256/                            ← UI 必须声明的副作用
关掉源站后重取仍 200                            ← 缓存命中确实不联网
签名改坏 → "plugin package is not trusted" → HTTP 422
```

## 四、方法论：这套流程里真正起作用的东西

写给下一个会话，因为这些是本会话花代价换来的。

### 1. 评审必须能自证，不能采信报告

本会话最有价值的几条发现，全部来自评审**自己动手**而非读报告：

- 交叉编译出 Linux test binary 实跑，发现「原子写」这条唯一防半份配置落盘的规则，**在 CI 唯一执行的平台上从来没有生效过**
- 跑 8 个变异的实测电池，而不是看代码猜哪条测试有效
- 手工走完四层错误链，确认代码**是对的**，然后问「谁会发现它被改坏」——答案是没人
- 去读 Wails v2.12.0 源码，推翻实现者「Wails 做不到结构化错误」的说法（它有 `ErrorFormatter`），并追出生产中 JS 侧收到的是**裸字符串而非 Error 实例**

### 2. 缺陷集中在「接缝」，而 per-task 评审对接缝结构性失明

每个 per-task 评审只看一个 task。最重的几条都出在任务之间：

- 「没有取消按钮」这条规则被 **Esc → 背景点击 → 标题栏 X → tab 按钮** 四扇门先后绕过。三条规则的测试全过，而它们保护的保证是开着的。漏检原因：组件测试全都**独立渲染**，bug 住在集成缝隙里——修复要求的测试必须**放进 `SettingsModal` 里**渲染。
- 一个守卫只守 `install` 不守 `grant`。发现 lost-update 时 `grant` 还不存在。

**全分支终审专职找接缝**，这是它存在的理由。

### 3. 反复出现的缺陷形状

- **断言了「该出现的出现了」，没断言「不该出现的没出现」。** 三个真机缺陷全是这一类：旧文案该消失、重试按钮该消失、无效请求该不发出。
- **`omitempty` 让空值变 `undefined`**，下游 `??` 回退到旧值。本会话踩了两次（`enabled` 与 `detail`）。凡是「false / 空串本身有意义」的字段，一律不加 omitempty。
- **一个按下去必然无效的控件就是在骗人。** 收敛期的取消按钮、不可信包的重试、无法取回时的「取回声明」——同一种错误的三次变体。

### 4. 我自己犯的错，写下来免得重犯

- **并行派发跨仓修复时，若一侧会改契约，另一侧必然看不到。** server 侧加了 `declared_error` 字段，GUI 侧并行跑不可能知道，结果 500 没了但诊断到不了屏幕。
- **plan 可以自相矛盾。** A5c Task 2 Step 1 把签名定死了、Step 4 却要求缓存命中解析，两者不可兼得——是评审发现的。
- **`-s` 这种缩写标志要查清楚再用。**
