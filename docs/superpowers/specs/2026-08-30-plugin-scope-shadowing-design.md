# per-agent 工具遮蔽设计（D2 spec）

**日期**：2026-08-30
**状态**：**已决策（2026-08-30）：不做。** 见第 5 节与第 6 节。
**上游**：`plans/2026-08-28-plugin-gap-closure-roadmap.md` 的「待决策 D2」；与 dsh Cordis 的比对结论「装载侧已比 Cordis 完整，差距全在扩展面的宽度」。

---

## 1. 问题

Cordis 允许**同名工具在某个 agent 内被替换**：`write_file` 对研究员 agent 是只读桩，对开发者 agent 是真写盘。Legion 今天只有减法：per-agent `disabled_tools` 把工具**拿掉**，没有换掉。

要不要做，路线图写得很准：技术上不难，**难在语义**——遮蔽会让「模型看到的工具」与「清单里的工具」不再一一对应。

## 2. Legion 今天已经有的

- **per-agent 禁用**：`agents.md` / agent 配置的 `disabled_tools`，装配期校验（名字必须在 gateable 目录里，打错字直接失败，不是静默无效），运行期经 `Registry.Without` 生效。
- **模式级收窄**：Plan 模式自动缩到只读子集（`Subset(SafeToolNames…)`）。
- **一种已存在的遮蔽**：任务注册表继承插件注册表时，**自身注册遮蔽同名继承项**（插件不能悄悄替换 `write_file`）。方向是固定的、全局的，不可配置。

也就是说：减法有了、模式收窄有了，**缺的正是「同一个名字、不同 agent、不同实现」**。

## 3. 三个方案

### A. 不做（维持现状）

要 per-agent 变体，就用**不同的工具名**（`write_file` 与 `write_file_dryrun`），靠 `disabled_tools` 各禁一个。

- **好处**：模型看到的名字与实际跑的东西永远一一对应。排查一个工具的行为，只需要看它的名字。
- **代价**：提示词里出现两个近义工具；模型可能挑错；两个名字的文档要各写一遍。

### B. per-agent 覆盖表（宿主配置说了算）

agent 配置里写映射：

```jsonc
"tool_overrides": { "write_file": "write_file_dryrun" }
```

含义：这个 agent 调用 `write_file` 时，实际派发 `write_file_dryrun`。模型仍然只看到 `write_file`。

- **必须同时做的三件事**（否则就是路线图担心的那种不可排查）：审计事件记录**两个**名字（模型叫的与实际跑的）；`GET /v1/plugins` 与 `agent` 配置面能列出当前生效的覆盖；被覆盖到的目标工具本身必须仍是这个 agent 允许调用的（覆盖不是提权通道）。
- **谁能写**：只有部署的 agent 配置。插件不能声明「我要替换 X」——那是 G4 spec §5 明确不做的那条（不可见的换掉的东西）。

### C. 全量 scope（Cordis）

插件也能在某个 scope 内注册同名实现，宿主按 scope 解析。

- 它把 B 的每一条安全要求都放大：替换的来源从「部署的配置文件」变成「任何装上的插件」，而模型与审计里看到的名字仍然不变。
- **本 spec 建议不做**，理由与 G4 spec 拒绝「插件替换宿主能力」相同：新工具是**可见的多出来的东西**，替换实现是**不可见的换掉的东西**。

## 4. 与既有决定的一致性

G4 spec §5 已经拒绝过一次同形状的东西（插件替换宿主能力）。D2 的 B 与它的区别只有一条，而这条是关键：**替换由部署自己写在配置里**，不是某个装上的插件自称。若连这条也放开（方案 C），两次决定就自相矛盾了。

## 5. 需要拍板的三件事

### 决策 A：做不做？做哪个？ —— **不做（方案 A）**

- **A 不做**（拍板选此）：不同变体用不同名字，靠 `disabled_tools` 分发。语义最简单，排查成本最低。
- **B per-agent 覆盖表**：能表达「同一个名字、不同 agent、不同实现」，代价是必须把可见性三件事一并做掉。
- **C 全量 scope**：与 G4 的既有决定冲突，除非有强需求。

### 决策 B / C：不适用

决策 A 选了「不做」，B 与 C 都是方案 B/C 内部的问题，随之作废。原文保留在下面，因为哪天要重开这个话题时，问题本身仍然是这两个。

### 决策 B（作废）：若做 B，模型该不该知道它在被覆盖？

- **不知道**（Cordis 的形态）：提示词里仍是 `write_file`。好处是 agent 定义可以复用同一套提示词。
- **知道**：目录里把它渲染成 `write_file（本 agent：dry-run 变体）`。模型据此调整措辞与预期，代价是提示词随 agent 变化（稳定前缀仍然稳定——它是部署级事实）。

### 决策 C（作废）：覆盖的目标可以是插件贡献的工具吗？

- **可以**：部署可以用一个插件工具替换内置工具的**本 agent** 行为。功能最强，但一次插件卸载会让该 agent 的这个名字突然失效（要定义：回落到原工具，还是这个 agent 的该工具直接不可用——**建议后者，fail-loud**）。
- **不可以**：覆盖只能指向另一个**内置**工具。语义最窄也最稳。

---

## 6. 决定与理由（2026-08-30）

**不做。** per-agent 的工具变体继续用**不同的名字**表达，靠 `disabled_tools` 分发到各 agent。

三条理由，按份量排：

1. **一一对应值这个价。** 今天「模型看到的名字」与「实际会跑的东西」是一对一的，排查一次异常行为只需要顺着名字走。覆盖表把这条打破，换来的只是提示词里少一个近义工具——一次排查的成本就够抵消很多次。
2. **它与 G4 的既有决定同形。** G4 spec §5 拒绝「插件替换宿主能力」的理由是：新工具是**可见的多出来的东西**，替换实现是**不可见的换掉的东西**。覆盖表的来源虽然更可信（部署自己的配置，不是某个装上的插件），但模型与审计看到的仍是同一个名字，那半个问题原样存在。
3. **减法已经够用。** `disabled_tools`（装配期校验、打错字直接失败）加上模式级收窄（Plan 只读子集），已经能表达绝大多数「这个 agent 不该做这件事」。真正只能靠覆盖表表达的是「这个 agent 做这件事时换一种做法」，而它可以用第二个名字表达。

**什么情况下重开这个话题**：出现一个真实需求，它同时满足 (a) 必须复用同一套 agent 提示词、(b) 变体差异大到不该由模型自己挑名字、(c) 运维接受审计里出现两个名字。三条缺一条，第二个工具名都是更便宜的答案。

到此路线图上的两个待决策项（D1、D2）都已回答：D1 做了命名服务（D1a + D1b 已交付），D2 不做。
