# 插件服务接缝设计（D1 spec）

**日期**：2026-08-29
**状态**：**待决策** —— 第 6 节的三个问题拍板之前不要动手（路线图 D1 原文就是这么写的）。
**上游**：`plans/2026-08-28-plugin-gap-closure-roadmap.md` 的「待决策 D1」；与 dsh Cordis 的比对结论「装载侧已比 Cordis 完整，差距全在扩展面的宽度」。

---

## 1. 问题

Cordis 的插件之间有**三角色契约**：服务定义、提供者、消费者。一个插件 `export const inject = ['agents']` 声明它需要 `agents` 这项能力，另一个插件把实现挂上去（`new SomeService(ctx, 'agents')`），`ctx.set('agents', undefined)` 就能整条换掉。消费者绑定的是**能力名**，不是某个具体实现。

Legion 的插件之间只有一条水平通道：`call_tool`，参数是**具体工具名**。插件 A 想用插件 B 的能力，就得写死 B 的工具名，并在 `plugin.json` 的 `requires` 里列出同一个名字。换一个实现 = 改所有消费者。

这就是 D1：**要不要让插件绑定「能力」而不是「某个具体工具」**。

## 2. Legion 已经有的那一半

值得先说清楚，因为它决定了 D1 的工作量比看上去小：

- **依赖生命周期已经在跑。** `plugin.json` 的 `requires` 列出本插件调用的工具名；`loader/depgraph.go` 的 `resolveStates` 做收敛：依赖不满足的插件进 `suspended`（不是卸载），提供方回来就 `resumed`。轮次有硬上限，环被单独识别并报错。
- **横向调用已经受管。** 插件的 `call_tool` 走宿主的注册表，与模型自己的调用同一条权限/策略/护栏/审计路径，并带 `plugin:<name>` 的调用来源。
- **贡献的撤回已经是原子的。** ledger owner 一撤，工具、gateable 目录项、observe/decide seam、提示词段一起消失。

**缺的只有「抽象」这一层**：`requires` 说的是「我要 `jira_search` 这个工具」，而不是「我要一个 issue-tracker」。

## 3. 与 Cordis 的处境差别（这条决定了不能照抄）

Cordis 的插件是**可信的同进程 TypeScript**。`ctx.set('web', impl)` 之所以便宜，是因为那个 impl 与宿主同源、同信任级别。

Legion 的插件是**不可信的 wasm**：它的能力是逐项授权的，它的每次调用都受审计，它的提示词段要打「untrusted」的围栏。让这样一个东西成为**宿主能力的实现方**，与让它贡献一个工具，不是同一个数量级的授权问题。

## 4. 三个方案

### A. 不做（维持现状）

插件之间继续按具体工具名耦合。

- **代价**：换实现要同时改提供者、每个消费者的 `requires`、以及消费者代码里写死的工具名。对「一个部署里只有两三个插件」的规模，这个代价很低。
- **好处**：没有任何新授权面。今天的模型是「插件贡献工具，宿主派发工具」，一句话说得清。

### B. 命名服务的间接层（**不碰宿主能力**）

`plugin.json` 增加两个字段：

```jsonc
"provides_services": ["issue-tracker"],   // 我能充当 issue-tracker
"requires_services": ["issue-tracker"]    // 我需要一个 issue-tracker
```

宿主把服务名解析成**当前提供者的工具集**，消费者通过一个稳定的名字调用（例如 `call_tool` 的 `tool_name` 允许写 `service:issue-tracker/search`）。生命周期直接复用 §2 的 `resolveStates`：没有提供者 → 消费者 `suspended`；提供者回来 → `resumed`。

- **授权面新增的只有一件事**：谁是 `issue-tracker`。这必须是**部署的决定**，写在 `plugins.json` 里，而不是插件自己抢注——否则装上一个插件就能顶替另一个插件正在提供的能力，消费者毫无察觉。
- **不允许**插件提供宿主内置能力（`fetch_url`、`read_file`、`browser_*` 等）的实现。宿主能力的实现方永远是宿主。

### C. 允许插件实现宿主能力（Cordis 全量）

插件可以成为 `web`、`fetch_url`、甚至记忆检索的实现方。

- **安全含义**：一个装上的插件就能接管宿主的对外访问路径。模型看到的工具名不变，审计里的来源不变（宿主工具），而背后执行的是插件代码。这与「插件贡献一个新工具」的区别是：新工具是**可见的多出来的东西**，替换实现是**不可见的换掉的东西**。
- 要做的话，至少需要：宿主能力的「可替换清单」（不在清单上的一律不可替换）、逐项授权、以及在审计与 `GET /v1/plugins` 里把「这个宿主能力当前由插件 X 实现」变成一等事实。
- **本 spec 的建议是不做**，直到有一个真实需求逼着做。

## 5. 明确不做（无论选哪个方案）

| 不做 | 为什么 |
|---|---|
| 插件自己抢注服务名 | 装上即顶替，消费者无从察觉 |
| 一个服务名同时有多个提供者并「自动选一个」 | 选择规则不可见 = 排查不可能；要多提供者就让部署明确列出优先级 |
| 服务解析绕过工具注册表 | 那条路径上挂着权限、策略、护栏、审计与 `disabled_tools`，绕过它等于让插件间的调用不受管 |
| 让消费者拿到提供者的**实例**（Cordis 的 `ctx.foo`） | 跨 wasm 实例的对象引用不存在；能传的只有一次调用与一份 JSON |

## 6. 需要拍板的三件事

### 决策 A：做不做，做哪个方案？

- **A 不做**：把 D1 从路线图上关掉，写明理由是「按工具名耦合的代价，在当前部署规模下低于新增一层间接的代价」。
- **B 做命名服务**（本 spec 的建议）：改动集中在 manifest 解析、`resolveStates` 的输入、以及 `call_tool` 的名字解析；不新增任何「插件替换宿主」的能力。
- **C 做全量**：需要先回答「宿主的哪些能力可以被替换」，这是一个产品与安全的联合决定。

### 决策 B：服务名由谁绑定？

- **部署钦定**（建议）：`plugins.json` 里写 `"services": {"issue-tracker": "legion-jira"}`，插件的 `provides_services` 只是**候选资格**，不是绑定。
- 插件自声明、先到先得：装上即生效，不需要运维动手——也意味着装上即可顶替。

### 决策 C：一个服务名允许几个提供者？

- **唯一**（建议）：解析结果确定，排查时「谁在提供它」只有一个答案。
- 多个 + 部署给出优先级：能表达 fallback，但排查时要先想清楚当时命中的是哪个。
