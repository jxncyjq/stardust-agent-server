## 〇、先读这条：一颗埋着的雷

**`Store.Refresh` 失败时的 fallback Trust 仍不携带撤销记录**（`internal/plugin/trustlist/store.go:256` 一带）。

S2 的最终复审抓到过一条 Critical：`Store.Current()` 在 `cache.read()` 出错时返回空 Trust，把 S1 的 `revoked-ever.json` 撤销累积集连坐扔掉——**删掉 `trustlist.json` 就能让被撤销钥匙签的包照常挂载**。那条已修（`12d75f0`）。

但 `Refresh` 那条路的 fallback Trust 是**同一个形状**，只是今天**没有任何调用方把它送进 `Merge`**，所以还不构成缺陷。**一旦有人送，那条 Critical 就以另一种拼法复活。**

下一步：要么让 `Refresh` 的 fallback 也带上撤销记录（与 `Current` 对齐），要么在类型上让「不带撤销记录的 Trust」进不了 `Merge`。**推荐后者**——前者是再修一次，后者是让这个形状不能再出现第三次。不需要拍板。

## 六、这一期最该带走的两条教训

### 1. 「规格明写、实现为零」只有整分支最终复审能抓到

S2 的那条 Critical：规格 §三③ / §八 明写「清单拉不到时撤销仍硬拒」，**实现与测试皆为零**。所以基线是**全绿**的——51 个包 ok、0 FAIL、`-race` 干净、`vet`/`gofmt` 都过——因为那条要求从头到尾没有任何代码，**没有任何测试会红**。

七个任务的逐任务复审全没抓住，因为**每个只看自己那块 diff**。同样的形状 S1 也栽过一次（规格 §7 第 2 步「serial 必须严格大于 git HEAD 那一版」从未实现，骗过计划自检和八轮任务复审）。

**判据：最终复审必须拿规格逐节点名，问「这一条有没有任何代码实现」。** 不是审 diff，是审覆盖。

### 2. 同一条不变量被绕过三次 = 守卫位置错了，不是补丁不够

「撤销了某把钥匙后，由它背书的实例就不该再服务」在 S2 里被绕过三次：

1. pass 2 压根不判已挂载的实例
2. 判了，但**判定寄生在磁盘那个包 `admit` 的成败上**（磁盘包先因 sha256 mismatch 失败，这一轮就永远拿不到撤销结论）
3. `restore` 把它挂回来

前两次的漏，**本质都是传参传错了对象**。终结办法不是在第三个 case 上再打一个补丁，而是**收口**：`revokedEndorsementOf(inst *instance)`——**签名收 `*instance`**，让「问的是这个实例自己的背书」在**类型上**成立；pass 2 / `sayWhichPackageWasRevoked` / `restore` 三处共用同一个。

**收全的判据**：数清所有能让一个实例处于挂载状态的写入点（`l.instances` 恰好两处：`activate` / `restore`），逐条证明都过了那个判定。

### 附：变异实证的纪律

本分支「**接缝在，但没人测那条接缝**」复发**八次**，**每一次都靠变异实证抓出来，静态审查一次都没抓住**。所以：

- 每条变异**必须 `go vet` 干净**——靠编译失败的变异什么都没证明
- **哪条变异之后测试仍然全绿，那条规则就没人守着，必须补测试而不是放过**（S2 里两次靠这条补出了真用例）
- **还原纪律**：每条变异从干净副本重新复制再打，还原后用 `md5sum` **且** `git diff` 确认回到提交态再跑下一条。**校验脚本本身要有它自己的失败判据**——本分支有人的还原脚本静默失败过，污染了后续几条变异，整轮作废
- **测退出码不要接管道**：管道会让 `$?` 取到 `tail` 的状态
