# D1a 实施计划：命名服务的声明、绑定与收敛

**日期**：2026-08-29
**上游**：spec `specs/2026-08-29-plugin-service-seam-design.md`，三个决策已拍板——做 **B（命名服务）**、**插件自声明先到先得**、**唯一提供者**。
**范围**：让插件按**能力名**而不是按具体工具名互相依赖。本期只做声明、绑定与生命周期收敛；`call_tool` 的 `service:` 名字解析是 D1b。

---

## 一、四条要立住的事实

1. **先到先得 ≠ 装上即顶替。** 唯一提供者的直接推论：第二个声明同名服务的插件**激活失败**，错误点名当前占用者。既不静默让位（那样「谁在提供它」说不清而两边都 loaded），也不静默顶替（那正是「部署钦定」选项要防的风险）。本仓对同名**工具**的既有做法本来就是 fail-loud 的冲突，服务名照此办理。
2. **「先到」按 `plugins.json` 的声明顺序**，不按挂载完成的时序。后者随机器负载变化，会让同一份部署两次启动的服务归属不同。
3. **无人提供 = 消费者挂起，不是卸载。** 直接复用 `loader/depgraph.go` 的 `resolveStates`：提供者回来就 `resumed`。这是 Legion 早就有的那一半，本期只是把「工具名」换成「服务名」喂给它。
4. **服务名与工具名是两个命名空间。** 一个插件可以提供服务 `issue-tracker` 而它的工具仍叫 `jira_search`；服务名不进 gateable 目录，也不出现在模型看到的工具清单里——模型看到的永远是工具。

## 二、任务

| # | 任务 | 关键测试 |
|---|---|---|
| T1 | manifest 的 `provides_services` / `requires_services`（校验：非空、无重复、不得自产自消） | 重复名被拒；自己 requires 自己 provides 的服务被拒（与 `requires` 对工具的既有规则一致） |

## 三、明确不做（本期）

- `call_tool` 的 `service:<名>/<能力>` 解析（D1b）。
- 服务名进 gateable 目录或模型的工具清单（见 §一.4）。
- 多提供者与优先级（决策 C 定了唯一）。
